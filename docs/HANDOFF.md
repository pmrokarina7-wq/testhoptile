# Передача проекта: ТЗ и приёмка для следующего исполнителя

Документ для того, кто продолжит работу над Vanguard Arsenal. Его цель — чтобы ты разобрался в репозитории за час, а не за день. Здесь описано, что сделано и как, как собирать и проверять мод, где подводные камни, как сдавать этапы владельцу и что делать дальше.

Состояние на 9 ноября 2026: **2.5.0-beta1**, PR #1–#4 слиты, релиз `v2.5.0-beta1` с zip лежит в GitHub Releases.

Читать в таком порядке:

1. `README.md` — что за мод, что готово, что осталось.
2. Этот файл.
3. `docs/VANGUARD-TZ.md` — рабочее ТЗ: статус по каждому разделу и порядок работ (§3).
4. `docs/TESTING.md` — проверка в игре и ожидаемые значения замеров.
5. `docs/vanguard-arsenal-plan.md` — исходное ТЗ (план v3). Это первоисточник цифр и замысла.
6. `docs/ART-BRIEF.md` — требования к арту и описание пайплайна моделей.

## 1. Проект за 5 минут

- **Что это:** контентный мод для Mindustry **v146** (ПК и Android), **без Java**. Внутри JSON-контент, один JS-скрипт (Rhino), PNG-спрайты, OGG-звуки и тексты RU/EN. Тема — Supreme Commander 2: UEF, Кибран, Эйон (T5), Серафим (T6).
- **Владелец** принимает работу по скриншотам из игры и по листам сверки арта. Пишет по-русски, коротко. Ему важно:
  - модели «на уровне Скорпиона», без халтуры;
  - **оптимизация**: мод должен идти на телефоне;
  - чтобы на GitHub всегда лежала актуальная версия;
  - работа без «роя» субагентов (это его прямая просьба). Один исполнитель ведёт этап последовательно.
- **Процесс:** один этап = одна версия = один PR. Перед PR сборка проходит серверную и клиентскую проверку в настоящей v146. Сливает владелец, либо ты, если он прямо попросил («залей, объедини»). После слияния выкладывается релиз с zip.

## 3. Окружение и команды

```bash
tools/setup-env.sh                                   # один раз (на чистой машине ставит пакеты через apt)
VG_BUILD=build/main tools/loadtest.sh                # ~30–60 с
VG_BUILD=build/main CLIENT_TIMEOUT=420 tools/clienttest.sh   # несколько минут
.venv/bin/python tools/art/g_beta1b.py               # перегенерировать спрайты этапа прямо в mod/sprites
VG_SPRITES=/tmp/spr .venv/bin/python tools/art/g_beta1b.py   # то же в другую папку — для сверки побайтно
```

Как читать результат:

- `loadtest.sh` → в выводе `1 mods loaded`, а в блоке `--- errors/warnings:` пусто. Любая строка `[W] Ignoring unknown field` означает опечатку в JSON-поле: игра молча его пропустила.
- `clienttest.sh` → в конце `[vgtest] finished, errors: 0`. В `build/main/shots/manifest.json` поле `errors` = `[]`, а значения в `mech` совпадают с ожидаемыми из `docs/TESTING.md`. Скриншоты в `build/main/shots/*.png` надо **открыть и посмотреть**.
- Строки `[vg] perf us/frame …` в `build/main/client.log` — профиль скриптов мода. Стенд включает его скрытой настройкой `vg-profile`.

Окружение, в котором работал прошлый исполнитель: Linux-песочница Hoplite, 64-bit, без GPU (llvmpipe), без звуковой карты. Ошибки `Failed to initialize audio` и `Failed to fetch community servers` в логе клиента — это нормально.

## 4. Как устроен `mod/scripts/main.js`

Один файл, разделы идут по этапам (поиск по `// ----`). Общие правила:

- **Каждая часть выключает только себя.** Обработчик обёрнут в `try/catch`, при ошибке ставит свой флаг `failX = true` и пишет `[vg] <что> disabled: <ошибка>`. Мод при этом продолжает работать. В логе стенда таких строк быть не должно.
- **Сервер и клиент.** Геймплей (урон, статусы, правило постройки) выполняется там, где `!Vars.net.client()`. Визуал и звук — там, где `!Vars.headless`.
- **`R(trigger, name, fn)`** вместо `Events.run`: та же подписка плюс замер времени по имени, когда включён `vg-profile`. Новые обработчики подключай через `R`, тогда они попадут в профиль.
- **Реестр построек:** `track("vg-имя")` один раз при загрузке скрипта, затем в обработчике `var list = blds("vg-имя")` и цикл с `if(!bd.isValid()) continue;`. **Не проходи `Groups.build.each` каждый кадр**: в больших базах это главная статья расходов. Реестр пересобирается, только когда появляется отслеживаемая постройка, плюс страховочный проход раз в 120 кадров.
- **Настройки:** объект `SET` (`supcom`, `shellfx`, `profile`) перечитывается раз в 120 кадров. Страница настроек создаётся в `ClientLoadEvent` в конце файла. Новая настройка = `checkPref` + ключи `setting.vg-…name/description` в обоих бандлах.
- **Таймеры считают игровое время:** `(tick += Time.delta) < N`, а не `++tick < N`. Подробности в подводных камнях.
- **Готовые механизмы, которые стоит переиспользовать:**
  - `ARTY[...]` — тень, метка падения и свист для артиллерии; достаточно добавить запись.
  - `interceptor(blockName, immuneBlocks)` — точечная ПРО по снарядам.
  - `dsInit` + обработчик `impacts` — один общий проход по снарядам на все эффекты попадания (ЭМИ, кванты и т. д.).
- **SupCom** (раздел Stage 2):
  - `ACU_MK` — марки БКМ, радиус и урон взрыва.
  - `ENG_MAX` — максимальный ярус постройки для каждого инженера.
  - `ITEM_TIER` — ярус предметов; ярус постройки = максимум по её цене.
  - `VGCORE` — ядра, которые включают режим.
  - Обработчик `buildRule` раз в 30 тиков пересчитывает команды и вешает скрытый статус `vg-supcom-nobuild`. Каждый кадр он чистит планы.
  - `UnitDestroyEvent` — взрыв БКМ и запрет постройки на 30 с.
  - `BlockBuildEndEvent` — апгрейд БКМ игрока при улучшении ядра.

## 5. Тестовый стенд (`tools/harness/scripts/main.js`)

Это отдельный мод `vgtest`. Он генерирует карту 330×340, раскладывает лаборатории, через `Time.time - t0` запускает события, делает скриншоты и в конце пишет `manifest.json`, после чего клиент закрывается.

Добавить проверку = 4 шага (образец — блок `beta-1 labs: engineer tiers…`):

1. `layoutX()` — расставить постройки и юниты; вызвать его из `setup()`.
2. `xUpdate(t)` — события по времени; вызвать из `mechUpdate()`. Действия «как у игрока», например планы постройки, добавляются из `Trigger.postDraw`, см. `beta1Plans()`.
3. `xReport()` — положить результаты в `mech.<имя>`; вызвать из `mechReport()`.
4. `addShot(имя, t0 + время, cx, cy, масштаб)` в `planShots()`, чтобы был скриншот.

После этого внеси ожидаемые значения в `docs/TESTING.md`.

- **Занятые зоны карты** (в клетках, приблизительно):
  - витрина всех блоков: y 0–45, ядра в ряду y≈6, юниты в ряду y≈37;
  - стрельбище: y≈90–130;
  - лаборатория механик: x 100–300, y 95–155;
  - лаборатории alpha4: x 8–110, y 196–232;
  - beta1: инженеры у (130–142, 155), ядро у (160, 168), поле ремонтников x 124–224, y 200–230;
  - T6: y 250–340.

  Точные позиции лежат в `manifest.blocks`.
- **Временная шкала** (t = `Time.time - t0`, тики, 60 = 1 с):
  - планы постройки при t > 120–130;
  - апгрейд ядра при t = 300;
  - БКМ лаборатории погибает при t = 400;
  - проверки запрета при t = 440–460;
  - реактор аннигиляции разрушается при t = 520;
  - последние кадры около t = 900.

  Новые события не должны конфликтовать с уже существующими.

## 6. Арт и звук

- **Арт.** Подробно описан в `docs/ART-BRIEF.md`; его обязательно прочитать перед любой моделью. Каждый ассет — отдельная low-poly 3D-модель в Python. Рендер ортографический сверху, 32 px на клетку, с AO и палитрой по материалам. Общие модули `geom`, `mats`, `rend`, `hero`, `export` менять осторожно: от них зависят все спрайты.
  - Генератор этапа (`tools/art/g_*.py`) пишет сразу в `mod/sprites` и создаёт листы сверки `build/art/<этап>-*.png`.
  - Повторный запуск на том же типе CPU даёт побайтно тот же результат. Проверка: `VG_SPRITES=/tmp/x …` и `cmp`. На другом CPU (AVX2 вместо AVX-512) могут разойтись единичные краевые пиксели — это нормально.
  - Эталон качества: `mod/sprites/blocks/turrets/scorpion-full.png`, `mantis-full.png`, `monolith-full.png`. Сравнение «было/стало»: `tools/art/compare.py`.
  - Спрайт мало сгенерировать — его надо **посмотреть в игре** на скриншотах витрины. Имена файлов и размеры холстов должны совпадать с тем, что ждёт JSON.
- **Звук.** `tools/sfx/sfxlib.py`: синтез на numpy, `save()` пишет OGG в `mod/sounds`. Новых звуков в beta1 нет: Мк II–III используют звуки Мк I.

## 7. Подводные камни (всё найдено на практике)

**Движок v146 и JSON**

- Неизвестное поле JSON **не ломает** загрузку, а молча пропускается (`[W] Ignoring unknown field`). Поэтому `loadtest.sh` должен проходить с нулём предупреждений.
- **Имена не должны совпадать с ванильными.** Поиск в v146 устроен неодинаково. Типизированные поля (`unitType`, `ammo` и т. п.) сначала ищут `vg-имя`, потом `имя`. А `find`/`locate` (цены, ссылки на контент) — сначала ванильное `имя`, потом `vg-имя`. Если имя совпадает с ванильным, одна ссылка уйдёт на ваниль, другая на мод. Пример: `electrolyzer` пришлось переименовать в `bauxite-electrolyzer`. Юниты и ядра в ссылках пиши с явным `vg-`.
- **HJSON:** значение без кавычек тянется до конца строки вместе с `}`. Однострочные объекты пиши только в JSON (`tools/relaxed2json.mjs`).
- Стены (`update = false`) **не попадают** в `Groups.build`. Простаивающие постройки (пустые конвейеры) движок «усыпляет» и тоже убирает оттуда. Нагрузочные тесты делай на постройках, которые обновляются постоянно, например на ремонтниках.
- У стен `canOverdrive = false`: движок каждый кадр сбрасывает им замедление, так что ЭМИ на стенах не проверить.
- Ванильный `enemyCoreBuildRadius` (50 клеток) отбрасывает планы постройки рядом с **вражеским** ядром.
- Порядок кадра в `Logic.update()`: сначала `Trigger.update` (наши скрипты), потом `Groups.update()` (юниты, постройки). Всё, что юнит делает в своём update, происходит **после** нашей проверки. Так `BuilderAI` в режиме помощи копировал чужие планы в обход правила SupCom. Поэтому запрет сделан статусом с `buildSpeedMultiplier = 0`: при нём `canBuild()` = false.

**Rhino (JS в Mindustry)**

- Java-поля читаются как свойства: `b.type`, `u.team`, `bd.block`. Вызов `b.type()` падает с TypeError — в alpha1 из-за этого отключались все механики.
- Если у класса есть и поле, и метод с одним именем, свойство оказывается функцией. Для этого есть хелпер `F(obj, "имя")`.
- `private`-поля недоступны (например, `unit.statuses`). Используй публичные методы: `hasEffect`, `getDuration`.
- `Number.toFixed()` оставляет одну значащую цифру (142,3 → «100.0»). Округляй через `Math.round`.
- `BulletType.create` с владельцем `null` неоднозначен для Rhino; создавай снаряд от имени постройки.

**Производительность**

- Не делай `Groups.build.each` и полных проходов по снарядам каждый кадр в каждом обработчике. Используй реестр (`track`/`blds`) и общий проход `impacts`.
- Статусы, которые обновляются «раз в N», должны жить дольше N **игровых тиков**. На телефоне при 10–20 FPS кадр длится 3–6 тиков; если считать кадры, статус спадёт между проходами. Этот баг был в beta1 и исправлен.
- Профиль в песочнице без GPU (0,6–1,1 мс на кадр на все скрипты при 3 300 постройках) — **не FPS телефона**. Телефон проверяет владелец.

**Стенд и клиент**

- При `infiniteResources` движок строит мгновенно, поэтому планы, которые надо проверить, добавляются в фазе отрисовки (`postDraw`).
- Камера клиента каждый кадр тянется к юниту игрока. Перед снимком стенд переносит игрока.
- `Team.green` обстреливают турели стрельбища. Тестовые юниты держи на `Team.sharded`, а инженерам назначай `AIController`: ИИ помощи сам чистит планы.
- Апгрейд ядра в стенде проверяется через `setBlock` + ручной `BlockBuildEndEvent`. Настоящая стройка ядра поверх ядра стендом **не покрыта**.
- Звука в песочнице нет, но клиент декодирует OGG при загрузке. Звук из «редких чистых тонов» ронял декодер v146 (alpha2). Держи под тонами шумовую подложку и гоняй `clienttest.sh` после любых изменений звука.

**Инструменты песочницы (если работаешь в Hoplite)**

- Политика блокирует инлайн-интерпретаторы (`python3 - <<EOF`, `bash -n …`). Пиши скрипт в файл (`/tmp/x.py`) и запускай его.
- `javap` нет. Исходники движка читай по тегу: `https://raw.githubusercontent.com/Anuken/Mindustry/v146/core/src/mindustry/...`. Так проверено всё, что перечислено выше.
- Клон репозитория неглубокий (depth 1). Для истории делай `git fetch --deepen=N`.
- Картинки для PR и README грузились как публичные ссылки. В репозиторий скриншоты не коммитятся, потому что `build/` в `.gitignore`.

## 8. Как сдавать этап (Definition of Done)

Этап принимается, когда выполнено **всё** из списка:

1. Версия поднята в `mod/mod.hjson` (`version` и начало `description`).
2. Новый контент:
   - JSON проходит `loadtest.sh`: `1 mods loaded`, 0 `[E]`, 0 `[W]`;
   - тексты есть в **обоих** бандлах;
   - спрайты сгенерированы скриптом из `tools/art`, и повторный запуск даёт тот же результат.
3. Механики на JS:
   - на каждую есть замер в стенде (`mech.*`), ожидаемые значения внесены в `docs/TESTING.md`;
   - `clienttest.sh` даёт `errors: 0` и ни одной строки `[vg] … disabled`;
   - **старые** замеры не сломались — сверь весь `mech` со списком в TESTING.md.
4. Оптимизация:
   - строки `[vg] perf` в логе стенда не хуже прошлого этапа (сейчас всего 0,6–1,1 мс на кадр, реестр ≤ 64 мкс);
   - новый покадровый обработчик подключён через `R`, а постройки берёт из реестра.
5. Новые модели и постройки просмотрены на скриншотах **из клиента**, а не только на листах сверки.
6. Обновлены:
   - `docs/VANGUARD-TZ.md`: шапка, §0, §1, статус раздела, §3;
   - `README.md`: «что сделано / не сделано / что осталось»;
   - этот файл, если появились новые подводные камни.
7. Коммит с понятным сообщением → PR в `baseline/2.5.0-alpha1`. В описании PR: что сделано, цифры проверки, скриншоты из игры и честный список «не сделано / не проверено».
8. После слияния — релиз с zip (пре-релиз до 2.5.0).

Что можешь проверить только ты, а что остаётся владельцу: телефон (FPS) и сетевая игра. Всегда пиши, что они **не проверены**.
